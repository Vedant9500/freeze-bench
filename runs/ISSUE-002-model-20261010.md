# ISSUE-002 — FTS AND-then-OR fallback with unclamped limits and hit-count-first fusion (model, 2026-10-10)
## Verdict / Answer
A typical multi-word natural-language query executes up to 2 sequential FTS queries (AND form, then OR fallback on empty), both at the full caller-controlled `lexical_k` LIMIT with no clamping on the `retrieve_findings` path, and a weak dual-hit (in both semantic and lexical lists) always outranks a strong single-hit because fusion sorts by the tuple `(hit_count, final_score)` where `hit_count` strictly dominates. Minimal fix: clamp all three k values into `[1, 200]` at `RetrievalEngine.search` entry (reusing the existing `_clamp_limit` policy); replace the two-round-trip AND-then-OR with a single OR query plus an AND-match boost (or a `LIMIT 1` AND existence probe); and sort fusion by `final_score` first with `hit_count` as tiebreak/small bonus. Tradeoff: ~halves FTS round-trips and bounds worst-case scans at the cost of a slightly larger single OR result set to re-rank, and strong-single relevance wins over weak consensus unless the dual bonus is tuned up.

## Changes (fix mode only: files + tests run)
N/A — research mode, no worktree edits made. Proposed minimal fix:
1. Limit policy: clamp `semantic_k/lexical_k/final_k` to `[1, FINDINGS_LIMIT_MAX=200]` at `RetrievalEngine.search`/`search_enhanced` entry (import/reuse `library._clamp_limit`); also clamp the oversampled `effective_semantic_k` after multiplication.
2. Fallback policy: single OR query per lexical search with an AND-match boost applied in Python (or a `LIMIT 1` AND existence probe before the full OR). Latency: 1 FTS round-trip always (vs up to 2 full-LIMIT scans today, ×variants under expansion); cost: OR returns the AND-superset with different FTS rank order, so AND-precision must be re-imposed by the boost.
3. Fusion ordering: `_sort = (final_score, hit_count)` or `final_score + 0.05*(hit_count==2)` bonus; keeps a consensus signal without letting it dominate. Ranking tradeoff: weak-dual no longer outranks strong-single by default; if consensus should matter more, raise the bonus explicitly and re-tune the 0.55/0.25/0.2 weights.

## Open questions
- FTS5 has no stemming (`reduce` ≠ `reduced`), which inflates the AND-miss rate beyond stopwords; a tokenizer/stemming change would alter how often the fallback fires but was not measured here.
- `final_k` slicing (`ranked[:final_k]`) with negative `final_k` silently drops tail items (e.g. `[:-1]`); clamping fixes this as a side effect — worth a dedicated edge test.
- Optimal dual-hit bonus weight needs graded relevance data; 0.05 is a starting guess, not measured.
