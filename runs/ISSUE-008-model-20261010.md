# ISSUE-008 — Ranking blend ignored by selection plus keyword safety (Muse Spark 1.3 Free, 2026-10-10)
## Verdict / Answer
Handoff selection ignores the pairwise blend: `rank_hypotheses` sorts by blended `final_score` (0.75·base + 0.25·comparison) but `_select_hypothesis_ids` sorts by `overall_score` (= `base_score` only), so the pairwise winner with lower base loses top_k handoff. The `_safety_score` keyword heuristic both over-blocks (negated "unsafe" → 0.2) and under-blocks (dual-use wording with no keyword → 1.0). Handoff (and final report) should sort by blended `final_score` with the same deterministic `(-final, -base, hypothesis_id)` tie-break, dedup should be an explicit thresholded pre-filter before top_k, and comparison `confidence` must be capped/priced per-judge so one confidence=1.0 vote cannot flip a base gap.

Interpretation: (a) Beta wins pairwise (confidence 1.0 → comparison 1.0 → final 0.803) and tops `rank_hypotheses`, but handoff's `(-overall_score=base, hypothesis_id)` key picks Alpha (base 0.775 > 0.7375) for top_k=1. (b) Benign note containing substring "unsafe" scores 0.2 (over-block); genuinely risky dual-use note with no listed keyword scores 1.0 (under-block).

Recommendations:
1. Handoff score: use blended `final_score` (same 0.75/0.25 weights, fallback to base when appearances==0); keep base-only as opt-in flag for ablation, and reuse `rank_hypotheses` rather than re-sorting `overall_score` in `orchestrator.py:847-850` and `reporting.py:152-155`.
2. Dedup threshold + tie-break deterministic: make threshold an explicit run-config (default 0.55 documented), pre-filter `near_duplicates` (keep highest-final per cluster) before top_k slice; unify every sort to `(-final_score, -base_score, hypothesis_id)` — current `hypothesis_id` tail is already deterministic but applied to different primaries.
3. Confidence-inflation pricing: cap per-comparison contribution (e.g. min(confidence, 0.75)), require ≥2 distinct `judge_agent`s or scale weight by `1/sqrt(appearances)`, log `(judge, confidence)` and add a `comparison_count` discount so one 1.0 vote cannot flip a ~0.04 base gap as above; consider Wilson-score or confidence-weighted blend weight instead of fixed 0.25.
