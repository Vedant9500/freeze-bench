# ISSUE-006 — Filtered poll_messages never advances offsets (Muse Spark 1.3 Free, 2026-10-10)
## Verdict / Answer
Filtered `poll_messages` (and `read_messages`) intentionally never persist the per-agent offset (`offset_updated=false` when `msg_types`/`from_agent` is set), so a worker polling e.g. `msg_types=["result"]` re-reads the same window forever (stored `last_seq` stays 0) while `wait_for_notification` still wakes on every sequence advance regardless of filter, causing spurious wakeups. The naive fix of advancing to the returned/filtered `last_seq` would silently consume and lose skipped types (task/artifact/system messages between polls would never be delivered to a later unfiltered read). The safe fix is per-filter offsets (or an explicit opt-in `advance`/`ack_seq`) plus filter-aware waiting, keeping the current no-advance default to avoid data loss.

## Changes (fix mode only: files + tests run)
No edits (mode `research`, `read_only: true`). Proposal only:

1. Keep no-advance as the safe default (prevents silent loss of skipped types). Add opt-in consumption: `poll_messages`/`read_messages(..., advance: bool=False, ack_seq: int|None=None)` — when `advance=True` persist `max(returned_last_seq)`; when `ack_seq` given persist it after the caller processes the batch. Document that naive `advance=True` marks every skipped `seq` in `(stored, returned]` as consumed, so a `result`-only consumer will never see interleaved `task`/`artifact`/`system` messages in a later unfiltered read (skipped-type loss).
2. Better default-safe alternative: per-filter offsets keyed `(session_id, agent_id, filter_fingerprint)` in `MessageBus.load_offset/save_offset` (`openlmlib/collab/message_bus.py:250,277`), with the unfiltered offset as the garbage-collection/high-water mark. Delivery-vs-efficiency: no loss (each filter has its own cursor, unfiltered cursor still sees everything), cost is N offset files/cursors per agent and a filter-canonicalization rule; cross-filter `has_more`/ordering stays per-cursor.
3. Make waiting filter-aware: pass `msg_types`/`from_agent` into `wait_for_notification` (or loop: wake on `seq>stored`, re-run filtered `read_new`, keep waiting until a matching row or deadline). Delivery-vs-efficiency: eliminates the Repro-B spurious wakeups and CPU/context churn, at the cost of slightly longer sleeps when only non-matching traffic arrives (correct for a filtered consumer) — must still not advance the stored offset on non-matching wakes.
4. Rejected naive fix: unconditionally `save_offset(returned_last_seq)` on filtered hits. Efficient (cursor always moves, no redelivery) but lossy: e.g. Repro A would jump 0→5 and the `task` seq 3 + `artifact` seq 4 would disappear from the next unfiltered read.
