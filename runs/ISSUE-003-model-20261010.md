# ISSUE-003 — rebuild_vector_index full re-embed with lost-update window (Muse Spark 1.3 Free, 2026-10-10)
## Verdict / Answer
Confirmed lost update: `rebuild_vector_index` snapshots DB ids, batch-encodes on a private empty store, then overwrites the index with `merge_existing=False`, so a finding inserted (DB-committed and even vector-flushed with `merge_existing=True`) mid-rebuild is present in SQLite but missing from the rebuilt index. Fix with a generation check + merge-on-save under the index lock (or chunked rebuild), not a bare overwrite; the pure-locking alternative is correct but stalls all writers for the whole encode.

## Evidence (`path:line` in worktree + what it proves)
- `openlmlib/library.py:73` — `def rebuild_vector_index(settings_path)` owns the whole race window.
- `openlmlib/library.py:74-76` — rebuild opens its **own connection** (`db.connect` + `db.init_db`), bypassing the shared `get_runtime()` state every writer (`add_finding`) uses; no shared lock is taken.
- `openlmlib/library.py:85` — rebuild starts from a **fresh empty store** (`create_vector_store(...)`), discarding all live vectors.
- `openlmlib/library.py:86` — snapshot point: `SELECT id FROM findings ORDER BY created_at ASC` frozen once; any later insert is invisible to this rebuild.
- `openlmlib/library.py:88-101` — collects `(finding_id, embedding_id, embedding_text)` only for snapshotted rows.
- `openlmlib/library.py:108` — long stall window: `embedder.encode(all_texts, batch_size=32)` (model encode of the whole library; cf. `openlmlib/embeddings.py:153` `SentenceTransformerEmbedder.encode`). Concurrent `add_finding` commits + flushes during exactly this call.
- `openlmlib/library.py:111-113` — `store.add(ids, vectors)` populates only the private snapshot store.
- `openlmlib/library.py:115-123` — `.bak` backup of index/meta is crash-safety only, not concurrency-safety.
- `openlmlib/library.py:126` — clobber: `save_vector_store(..., merge_existing=False)` unconditionally overwrites the on-disk index with the stale snapshot.
- `openlmlib/library.py:73-152` (whole function) — contains **zero** `write_lock` / `interprocess_lock` acquisitions (verified by grep: locks appear at `openlmlib/library.py:655,751,765,769,867,947,1091,1168` for all other write paths, never inside rebuild).
- `openlmlib/vector_store.py:303-312` — `save_vector_store(store, index_path, meta_path, merge_existing=True)` takes `interprocess_lock` only for the brief file-write section, so rebuild's snapshot→encode→save sequence is unlocked.
- `openlmlib/vector_store.py:317-343` — the `merge_existing=True` path (load existing + apply pending adds/deletes) is what preserves concurrent writers; rebuild explicitly opts out of it.
- `openlmlib/vector_store.py:40` (`test_rebuild_save_replaces_stale_vectors`) — documents that `merge_existing=False` is intended to drop stale vectors, which is exactly the mechanism that also drops live concurrent vectors.
- `openlmlib/library.py:751-757` — concurrent writer path (`add_finding`): `db.insert_finding` + `store.add` + `mark_dirty` + `maybe_flush(force=True)` commits to DB immediately and flushes the vector via the merge path.
- `openlmlib/runtime.py:30` — `write_lock: RLock` guards writers; rebuild never acquires it.
- `openlmlib/runtime.py:199-212` — `maybe_flush(force=True)` calls `save_vector_store(state.store, ...)` with default `merge_existing=True`, i.e. the concurrent flush my repro performs mid-rebuild is the normal production behavior — and it still gets overwritten.
- `openlmlib/file_lock.py:54-96` — `interprocess_lock` exists and is suitable for the fix, but rebuild only inherits it transiently inside the final save.

## Changes (fix mode only: files + tests run)
Research mode — no worktree edits made; no tests run beyond the `/tmp` repro above.

Proposed fix (not applied):
1. **Generation check + merge-on-save (recommended).** Record `max(created_at)` / id-set (or a `PRAGMA data_version` / row count) at snapshot (`openlmlib/library.py:86`); after encode and before save, re-query for ids not in the snapshot; embed just the delta and `add` it to the rebuilt store, then save with `merge_existing=True` while holding `interprocess_lock` (extend the lock in `openlmlib/vector_store.py:312` to cover read-modify-write, or acquire it in rebuild across the delta-save). Handle deletes explicitly: compute `on_disk_ids - live_db_ids` and `store.delete(stale)` instead of relying on blind overwrite to drop them. *Tradeoff: stall ≈ only the short locked delta-save (ms), memory = snapshot + O(delta), correctness = no lost adds; delete handling must be explicit.*
2. **Chunked rebuild.** Encode/save in N-row chunks each merged (`merge_existing=True`). *Tradeoff: bounded memory and smaller per-chunk lock hold, but more I/O round-trips and still needs the generation check for the tail chunk.*
3. **Coarse locking (simplest, worst stall).** Hold `runtime.write_lock` + `interprocess_lock` for the entire snapshot→encode→save. *Tradeoff: trivially correct, but stalls every writer for the full batch encode (seconds–minutes on large libraries) and risks lock timeouts (`openlmlib/file_lock.py:81-82` 30–60 s defaults) — rejected for production.*
